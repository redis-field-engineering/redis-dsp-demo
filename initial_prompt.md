You are building a production-shaped prototype for a Redis-based DSP candidate generation + reranking system.

Goal
Build a reproducible local demo that shows:
1) how Redis Sets can be used for candidate generation,
2) how a lightweight reranker works in Python,
3) how latency behaves under load,
4) how ranking quality can be evaluated on synthetic data and on a translated Hugging Face clickstream-style dataset.

Primary constraints
- Use Redis 8.6 in Docker Compose for local development/demo.
- Keep the local dataset and Redis memory footprint reasonable, ideally <= 6 GB total in the local demo.
- The design must also be able to scale up conceptually to a Redis Enterprise cloud deployment with much larger data.
- Expose metrics via OpenTelemetry.
- Run Prometheus and Grafana locally in Docker Compose.
- Include notebooks so the architecture and evaluation are easy to understand.
- Include a load test that can generate a configurable request throughput and report average, p95, and p99 latency.
- Start with a synthetic dataset generated by the repo.
- Also add a path to examine a Hugging Face clickstream/click-log dataset and translate it into the same ad-targeting domain so we can compare ranking quality.
- Evaluate ranking quality with NDCG and at least one classification-style metric such as F1, Precision@K, or Recall@K.
- Keep the prototype understandable, well-structured, and easy to extend.

Architecture to implement

Redis data model
Use Redis Sets for exact candidate generation:
- campaign index sets by criterion, e.g.:
  - idx:geo:US
  - idx:device:iOS
  - idx:interest:camping_high
  - idx:interest:home_improvement_high
- user profile hashes or JSON for user features:
  - user:<id>
- campaign hashes or JSON for campaign attributes and rerank weights:
  - campaign:<id>

Candidate generation flow
- For each request, read the user’s top few hard filters / strong signals.
- Use Redis SINTER or equivalent set algebra to get a small candidate pool.
- Keep the candidate pool capped, e.g. 50 to 200 campaigns.
- Do not loop over all campaigns in the hot path.
- The design should support a small local campaign universe and also a much larger cloud deployment conceptually.

Reranking flow
- Fetch candidate campaign metadata in one batch.
- Score candidates in memory with a simple transparent model:
  - weighted dot product or linear scoring is fine
  - include bid as one factor
  - optionally include a small freshness/frequency adjustment
- Return the top K ads, typically top 3 or top 5.

API requirements
Expose a simple HTTP service, for example with FastAPI:

- POST /rank
  - input: user_id
  - output: candidate IDs, reranked top IDs, scores, and timing breakdown
- POST /batch-score
  - optional endpoint for offline or debug scoring

## Example User and Campaign Schema

Use these as reference shapes for both the synthetic dataset and the Redis key design.

### User Profile (stored in Redis as HASH or JSON)

user:123 {
  "geo": "US",
  "device": "iOS",
  "age_bucket": "25-34",

  "interests": {
    "camping": 0.82,
    "home_improvement": 0.74,
    "gaming": 0.21
  },

  "segments": [
    "camping_high",
    "home_improvement_high"
  ]
}

Notes:
- "interests" are continuous scores (0–1) used in reranking.
- "segments" are coarse buckets used for candidate generation (set membership).
- In Redis, this can be flattened:
  HSET user:123 camping 0.82 home_improvement 0.74 gaming 0.21 geo US device iOS
  or stored as JSON if RedisJSON is used.

---

### Campaign / Ad Schema (stored in Redis as HASH or JSON)

campaign:c1 {
  "geo": ["US", "CA"],
  "device": ["iOS"],

  "required_segments": [
    "camping_high"
  ],

  "weights": {
    "camping": 1.2,
    "home_improvement": 0.3,
    "gaming": -0.2
  },

  "bid": 2.50,
  "campaign_id": "c1"
}

Notes:
- "geo", "device", etc. are hard filters → used in Redis Sets.
- "required_segments" map directly to inverted indexes:
  SADD idx:segment:camping_high c1
- "weights" are used in reranking (dot product with user features).
- "bid" is included in final scoring.

---

### Redis Inverted Index Examples (Candidate Generation)

SADD idx:geo:US c1 c2 c3
SADD idx:device:iOS c1 c4 c8
SADD idx:segment:camping_high c1 c7 c9
SADD idx:segment:home_improvement_high c1 c3

---

### Example Candidate Generation Query

SINTER idx:geo:US idx:device:iOS idx:segment:camping_high

Returns a small set of candidate campaign IDs.

---

### Example Reranking Logic (Conceptual)

score = 0
for feature, value in user["interests"].items():
    score += value * campaign["weights"].get(feature, 0)

score += campaign["bid"]

---

### Optional Cached Top-K per User (Sorted Set)

ZADD user:123:top_campaigns 3.12 c1
ZADD user:123:top_campaigns 2.98 c9

---

### Synthetic Data Expectations

- Users:
  - have 5–20 interest features
  - mapped into 1–5 segments (e.g. "_high", "_medium")
- Campaigns:
  - target 1–3 segments
  - include 5–20 weighted features
- Ground truth:
  - generated via a noisy dot-product model:
    click = sigmoid(user ⋅ campaign + noise)

---

This schema must be used consistently across:
- synthetic data generator
- Redis key schema
- API inputs/outputs
- notebooks
- evaluation code
